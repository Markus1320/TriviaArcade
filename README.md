# TriviaArcade

An open source trivia game in the style of classic arcade cabinets. Topics are geography
and history. Questions are generated by an LLM from a knowledge graph built from
[Wikidata](https://www.wikidata.org/), and a second LLM call judges your answers.
One wrong answer ends the run. Your streak is your score.

> Status: milestone 4 (game loop). The full game is playable in a plain, unstyled UI:
> start a run, answer until the first mistake, save the score under a handle, and see the
> top 10. The arcade look follows in milestone 5.

## Architecture

```
Browser (any device on the home network)
        |
      Caddy  :8080  (static frontend + reverse proxy, the only published port)
        |
       /api -> backend (FastAPI)
                 |          |            |
               Neo4j    PostgreSQL    Ollama API
```

| Service    | Purpose                                   | Ports                                         |
|------------|-------------------------------------------|-----------------------------------------------|
| `caddy`    | Serves the built frontend, proxies `/api` | `0.0.0.0:8080` (configurable via `CADDY_PORT`) |
| `backend`  | FastAPI app                               | internal only                                 |
| `neo4j`    | Knowledge graph (rebuildable)             | `127.0.0.1:7474`, `127.0.0.1:7687`            |
| `postgres` | Players, runs, leaderboard, logs          | internal only (see debugging below)           |

## Requirements

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) with Docker Compose
- For local development outside Docker:
  - [uv](https://docs.astral.sh/uv/) (installs Python 3.12 for you)
  - Node.js 22 and npm

## Setup

1. Copy the environment template and fill in values:

   ```bash
   cp .env.example .env
   ```

   Set `POSTGRES_PASSWORD` and `NEO4J_PASSWORD` (Neo4j requires at least 8 characters),
   and the Ollama values (see [Configuration](#configuration)); without them the stack starts,
   but no questions can be created. Never commit `.env`.

2. Start the stack:

   ```bash
   docker compose up --build
   ```

3. Build the knowledge graph once (see below): `docker compose run --rm importer`.

4. Open <http://localhost:8080> and press START. The health endpoint
   <http://localhost:8080/api/health> reports whether both databases are reachable.

If port 8080 is already in use, set `CADDY_PORT` in `.env` (for example `CADDY_PORT=8081`).

## Building the knowledge graph

The graph is imported from Wikidata into Neo4j. Content and balance are controlled by
[config/import.yaml](config/import.yaml): entity types with fame thresholds, the relation
allowlist, numeric facts, years and alias languages. The graph holds rebuildable data only;
every import replaces it completely.

```bash
docker compose run --rm importer
```

The first run queries the public Wikidata endpoint and takes several minutes. Raw responses
are cached in `data/raw/` (gitignored), so later runs with the same config are fast and do not
hit Wikidata again. The container writes the cache into the mounted `data/` folder; on a
Linux host, make sure that folder is writable for the container user. Useful options:

```bash
docker compose run --rm importer python -m importer --dry-run   # build and print stats only
docker compose run --rm importer python -m importer --refresh   # ignore the cache
```

The importer can also run on the host against the Neo4j port bound to `127.0.0.1`
(credentials come from `.env`):

```bash
cd backend
uv run python -m importer
```

Browse the result in the Neo4j Browser at <http://localhost:7474>, for example:

```cypher
MATCH (c:Country {label: "France"})-[r]-(n) RETURN c, r, n
```

Every node has the label `Entity` plus a type label (`Country`, `City`, `Person`, ...) and
the properties `wikidata_id`, `label`, `aliases`, `description`, `sitelinks` (fame score),
`entity_type` and `seq` (dense number for random selection), plus years and numeric facts
where available. Relationship types come from the allowlist (`CAPITAL`, `SHARES_BORDER_WITH`,
...) and carry the Wikidata `property` and, where known, `start_year`, `end_year` or `year`.
Negative years are BCE.

## Playing

Open <http://localhost:8080> (or `http://<host-ip>:8080` on a phone, see below), press START
and type your answers. Each correct answer adds one to your streak; the first wrong answer
ends the run and shows the correct answer. Then save your score under a handle (3 to 8
letters or digits) or pick one used before. The leaderboard shows the top 10 runs; ties go
to the run that finished first.

If the judge is not reachable, the run is paused instead of ended: send the answer again.
Reloading the page resumes the current run with the same question.

### API

All endpoints live under `/api`:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/runs` | start a run, returns `run_id` |
| `GET` | `/runs/{run_id}` | run state, including the open question (for reloads) |
| `POST` | `/runs/{run_id}/question` | next question; returns the open one if unanswered |
| `POST` | `/runs/{run_id}/answer` | `{"answer": "..."}` (1 to 200 characters), returns the verdict |
| `POST` | `/runs/{run_id}/claim` | `{"handle": "..."}` after game over, once per run |
| `GET` | `/leaderboard` | top 10 runs |
| `GET` | `/players` | existing handles, most recently used first |

Errors return `{"code": "...", "detail": "..."}`, e.g. `judge_unavailable` (503) or
`run_already_claimed` (409). Expected answers are only sent once the run is over.

## Questions from the LLM

Questions are generated in two independent LLM calls through the Ollama API:

1. A random walk picks a starting entity (first a random entity type, then a random entity,
   so large types do not dominate) and walks 1 to 3 hops through the graph.
2. The generator model writes a question from these facts, returned as JSON (question,
   expected answer, accepted answers, numeric range) and validated.
3. The judge model decides whether a player's answer is correct and may only reply `true` or
   `false`. The player's answer is treated as untrusted data inside clear delimiters.

Prompts live in [backend/prompts/](backend/prompts). Every call is logged in the PostgreSQL
table `llm_calls` (prompt, raw output, parsed result, model, latency).

### Configuration

Set these in `.env` (see `.env.example`):

- `OLLAMA_API_KEY`: your Ollama API key
- `OLLAMA_BASE_URL`: `https://ollama.com` for the cloud API
- `LLM_GENERATOR_MODEL` and `LLM_JUDGE_MODEL`: model tags your account can use. List them
  with `curl -H "Authorization: Bearer $OLLAMA_API_KEY" https://ollama.com/api/tags`.

Restart the backend after changing `.env`: `docker compose up -d`.

### Question difficulty

Difficulty is mainly controlled by which facts the random walk picks, set in `.env`:

- `WALK_TOP_SHARE` (default `0.5`): only the most famous share of each entity type (cities,
  battles, rivers, ...) is used. Fame is compared within a type. Lower is easier.
- `WALK_MIN_HOPS` / `WALK_MAX_HOPS` (default `1` / `2`): how many relations a question may
  connect. Fewer hops give simpler questions.

Try a setting with the sample script (`--seed` makes runs comparable), then restart the
backend with `docker compose up -d` so the game uses it.

### Reviewing sample questions

This script calls the real LLM and prints generated questions for a human to review. It is
never part of CI.

```bash
docker compose run --rm backend python -m scripts.sample_questions --count 10 --judge
```

`--judge` also runs the judge on the expected answer (should be `true`), a wrong answer and
a prompt injection attempt (both should be `false`). `--seed 42` makes the walks
reproducible, `--no-log` skips the call log.

To look at logged calls:

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT id, purpose, model, attempt, latency_ms, parsed, error FROM llm_calls ORDER BY id DESC LIMIT 20"'
```

## Playing from a phone on the home network

1. Find the host's local IP address. On Windows run `ipconfig` and use the IPv4 address
   of your Wi-Fi or Ethernet adapter (for example `192.168.178.x`). Ignore virtual
   adapters such as VirtualBox (`192.168.56.x`) or WSL/Hyper-V (`172.x.x.x`).
2. On the phone, connected to the same Wi-Fi, open `http://<host-ip>:8080`.
3. If it does not load, allow inbound TCP on the Caddy port in the Windows firewall
   (Docker Desktop usually does this for you), and make sure the network is set to
   "Private" in Windows.

Only Caddy is reachable from the network. Neo4j is bound to `127.0.0.1`, PostgreSQL is
not published at all.

## Development

### Backend

```bash
cd backend
uv sync
uv run ruff check .
uv run ruff format .
uv run mypy
uv run pytest
```

Add dependencies with `uv add <package>` (or `uv add --dev <package>`), never with plain `pip`.

### Frontend

```bash
cd frontend
npm install
npm run dev          # Vite dev server, proxies /api to the running stack on :8080
npm run lint
npm run format:check
npm run build        # type check and production build
```

### Database migrations

PostgreSQL schema changes go through Alembic (`backend/alembic/`). The backend container
applies pending migrations on start. To create a new migration after changing
`app/db/models.py`, rebuild the image and let Alembic compare models and database; the
migrations folder is mounted so the new file lands in the repository:

```bash
docker compose build backend
docker compose run --rm -v ./backend/alembic:/app/alembic backend alembic revision --autogenerate -m "describe the change"
```

Review the generated file before committing. `docker compose exec backend alembic check`
verifies that models and migrations match.

### Debugging the databases

- Neo4j Browser: <http://localhost:7474> (log in with `NEO4J_USER` / `NEO4J_PASSWORD`).
- PostgreSQL on `127.0.0.1` (set `POSTGRES_DEBUG_PORT` if 5432 is already in use):

  ```bash
  docker compose -f docker-compose.yml -f compose.debug.yml up -d
  ```

### CI

GitHub Actions runs linters, type checks and tests for backend and frontend and
validates the Compose files on every push.
